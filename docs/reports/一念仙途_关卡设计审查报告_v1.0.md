# 一念仙途 — 关卡设计审查报告与优化方案 v1.0

> 审查人：LevelDesigner（关卡设计师视角）
> 审查日期：2026-07-01
> 审查范围：游戏流程架构、秘境关卡、章节里程碑、战斗遭遇、场景叙事、节奏控制
> 审查方法：代码审计 + 数据结构分析 + 流程图推演

## 〇、审查结论速览

| 维度 | 成熟度 | 评级 | 核心问题 |
|------|--------|------|----------|
| 章节里程碑系统 | ★★★☆☆ | B | 阈值设计机械，6章用同一套模板，无节奏变化 |
| 秘境（Dungeon）关卡 | ★★☆☆☆ | C+ | 全部3-4节点线性结构，零分叉、零变化 |
| 卡牌流节奏控制 | ★★★☆☆ | B- | 20级优先级系统精细，但叙事预算是创可贴不是解药 |
| 战斗遭遇设计 | ★★☆☆☆ | C | 纯数值对撞，无空间战术、无telegraph、无退路设计 |
| 场景/位置叙事 | ★☆☆☆☆ | D | 系统建好了几乎没接通，位置切换几乎不发生 |
| 流程可读性 | ★★☆☆☆ | C | 玩家无法区分主线/支线/随机，无进度可视化 |
| 转世难度曲线 | ★★★☆☆ | B | 乘数缩放可用但粗糙，无空间维度的难度调节 |

**总评**：系统架构扎实（20级优先级+叙事预算+因果链），但"关卡"层面的设计思维几乎缺席。当前游戏的"关卡"不是被设计出来的，而是被数据结构自动生成的。需要从**空间节奏、流程分叉、遭遇可读性、环境叙事**四个维度做深度重构。

## 一、章节里程碑系统审查

### 1.1 现状分析

**文件**：`src/systems/RealmChapterSystem.js` + `data/cards/chapter_milestones.json`

六章结构：
```
第一章：凡尘初醒（炼气）→ 宗门风云（筑基）→ 丹心问道（金丹）
→ 碎丹成婴（元婴）→ 神游太虚（化神）→ 天劫飞升（渡劫）
```

每章5个里程碑卡，修为阈值固定为 `[20, 40, 60, 80, 100]`。

### 1.2 发现的问题

#### 问题A：阈值设计完全机械重复

```javascript
// RealmChapterSystem.js 第20-62行
// 六个境界全部使用同一套阈值
milestones: [20, 40, 60, 80, 100]
```

**问题本质**：六个章节的节奏弧线完全相同。这意味着：
- 第一章（新手期）和第六章（终局期）的里程碑间距一模一样
- 没有体现"越到后面越难"的修仙核心体验
- 玩家在第六章依然每20修为就触发一个里程碑，节奏感与第一章无差异

**关卡设计原则违反**：Pacing Arc 要求不同章节有不同的紧张-释放节奏。新手期应该密集给反馈（短间距），终局期应该拉长间距制造"漫长苦修"的压迫感。

#### 问题B：里程碑触发无玩家主动权

```javascript
// game.js 第560-573行
const cultivation = gameState.getAttribute('cultivation');
const threshold = chapterSystem.shouldTriggerMilestone(gameState.realm, cultivation);
if (threshold !== null) {
  const milestoneCard = chapterSystem.getMilestoneCard(gameState.realm, threshold);
  // 强制注入，玩家无法选择"现在触发"还是"稍后再说"
}
```

**问题本质**：里程碑是纯被动触发——修为到了就弹，玩家无法延迟。这导致：
- 玩家可能在连续3轮内打出高修为效果卡，一口气触发2-3个里程碑卡，叙事密度爆炸
- 与叙事队列（_narrativeQueue）的卡牌叠加，造成"一轮弹5张叙事卡"的雪崩

#### 问题C：场景图严重复用

```javascript
// RealmChapterSystem.js 第69-111行 SCENE_FALLBACK_MAP
// 30张里程碑卡共用10张图片
'ch_qi_20':   'assets/cards/events/scene_qi_q_start_sword.png',
'ch_foundation_20':  'assets/cards/events/scene_qi_q_elder.png',  // 与 qi_60 同图
'ch_foundation_40':  'assets/cards/events/scene_qi_q_demon.png',
```

**问题本质**：从空间叙事角度看，场景图就是"玩家看到的空间"。30张卡只有10张视觉，意味着玩家在不同章节看到一模一样的"空间"，破坏沉浸感。

### 1.3 优化建议

#### 建议A：差异化阈值曲线

```javascript
const CHAPTER_DEFINITIONS = {
  qi:          { milestones: [15, 30, 50, 70, 100] },  // 新手期密集反馈
  foundation:  { milestones: [20, 40, 60, 80, 100] },  // 标准节奏
  golden:      { milestones: [20, 45, 65, 85, 100] },  // 中期拉长
  nascent:     { milestones: [25, 50, 70, 90, 100] },  // 苦修感
  deity:       { milestones: [30, 55, 75, 95, 100] },  // 更长
  tribulation: { milestones: [20, 40, 60, 80, 100] },  // 终局回归标准但内容更重
};
```

#### 建议B：里程碑缓冲机制

在 `shouldTriggerMilestone` 中加入"缓冲轮数"——修为达标后，等待1-3轮自然卡牌再触发里程碑，避免叙事雪崩。

## 二、秘境（Dungeon）关卡审查

### 2.1 现状分析

**数据位置**：各境界JSON的 `dungeons` + `dungeonCards` 字段

当前秘境结构一览：

| 境界 | 秘境名 | 节点序列 | 分叉 | 可选路径 |
|------|--------|----------|------|----------|
| 炼气 | 古洞探险 | event→battle→reward (3节点) | 无 | 无 |
| 筑基 | 神秘秘境 | event→battle→reward (3节点) | 无 | 无 |
| 金丹 | 太古遗迹 | event→battle→choice→reward (4节点) | 无 | 无 |
| 金丹 | 剑意秘境 | (类似结构) | 无 | 无 |
| 元婴 | (数据存在) | 类似线性结构 | 无 | 无 |
| 化神 | (数据存在) | 类似线性结构 | 无 | 无 |
| 渡劫 | (数据存在) | 类似线性结构 | 无 | 无 |

### 2.2 发现的问题

#### 问题A：全部秘境都是无分叉线性管道

```
[入口] → [事件] → [战斗] → [奖励] → [出口]
```

**关卡设计原则违反**：
- **Critical Rule**: "Every junction must offer a clear primary path and an optional secondary reward path"
- 当前秘境没有任何junction，玩家没有任何选择权——进秘境后就是一条路走到底
- 对比《杀戮尖塔》(Slay the Spire)的地图设计：每个节点都有2-3条路径选择，玩家可以在"战斗→商店→事件→休息"之间做风险决策

#### 问题B：节点类型极度单一

所有秘境的节点类型只有三种：`event`、`battle`、`reward`。

**缺失的节点类型**：
- `rest`（休息点：恢复资源、整理装备）
- `shop`（秘境内商店：紧急补给）
- `elite`（精英怪：高风险高回报）
- `boss`（秘境Boss：不同于普通战斗的终极遭遇）
- `trap`（陷阱节点：纯惩罚，测试玩家预判）
- `mystery`（神秘事件：未知结果）
- `fork`（分叉选择点：选择走哪条路）

#### 问题C：秘境推进逻辑是纯线性递增

```javascript
// CardSystem.js 第848-858行
advanceDungeon() {
  gameState.dungeonNodeIndex++;
  // 只是+1，没有任何分支逻辑
  if (!dungeon || gameState.dungeonNodeIndex >= dungeon.nodes.length) {
    gameState.dungeon = null;  // 走完了就退出
  }
}
```

**问题本质**：这不是"关卡设计"，这是"队列遍历"。玩家在秘境中的体验等同于依次翻开一叠卡牌，没有任何空间感。

#### 问题D：秘境入口无前置条件

```javascript
// game.js 第670-674行
if (choice.dungeon) {
  gameState.dungeon = choice.dungeon;
  gameState.dungeonNodeIndex = 0;
  // 直接进入，没有任何"准备阶段"
}
```

**问题本质**：进入秘境没有准备阶段、没有资源门槛、没有"你确定要进入吗？"的决策窗口。从关卡设计角度，这违反了"entry read time"原则——玩家需要知道"进去了会面对什么"。

### 2.3 优化建议

#### 建议A：引入分叉型秘境地图

```json
{
  "ancientCave": {
    "name": "古洞探险",
    "description": "你站在古洞入口，冷风从洞中吹出。前方似乎有两条路……",
    "entryCard": "cave_entry",
    "nodes": {
      "start": {
        "type": "fork",
        "card": "cave_fork1",
        "branches": { "left": "cave_deep", "right": "cave_river" }
      },
      "cave_deep": {
        "type": "battle",
        "card": "cave_beast",
        "next": "cave_reward_deep"
      },
      "cave_river": {
        "type": "event",
        "card": "cave_spirit",
        "next": "cave_fork2"
      },
      "cave_fork2": {
        "type": "fork",
        "card": "cave_fork2_card",
        "branches": { "left": "cave_reward_river", "right": "cave_boss" }
      },
      "cave_reward_deep": { "type": "reward", "card": "cave_treasure_deep" },
      "cave_reward_river": { "type": "reward", "card": "cave_treasure_river" },
      "cave_boss": { "type": "boss", "card": "cave_boss_card" }
    }
  }
}
```

#### 建议B：秘境入口前置卡

在 `choice.dungeon` 触发时，先插入一张"秘境入口卡"，让玩家选择"准备后进入"或"直接进入"或"放弃"。

## 三、卡牌流节奏控制审查

### 3.1 现状分析

**文件**：`src/systems/CardSystem.js` (20级优先级) + `src/game.js` (叙事队列)

当前优先级体系：
```
100 → 死亡卡
 90 → 瓶颈卡
 80 → 支线当前卡
 70 → 支线入口卡
 60 → 因果卡
55-42 → 叙事弧线卡（道侣/师尊/盟友/先知）
40-28 → 次要叙事卡（势力/NPC/场景/回响）
 25 → 商店卡
 20 → 集市卡
 10 → 普通卡
```

叙事预算系统：重大叙事消耗3点，次要消耗1点，每轮恢复1点，上限5点。

### 3.2 发现的问题

#### 问题A：叙事预算系统无法控制"情绪密度"

```javascript
// CardSystem.js 第95-113行
_canAffordNarrative(priority) {
  if (priority >= 60) return true;  // 系统卡不受限
  if (isMajor) return this._narrativeBudget >= 3;
  if (isMinor) return this._narrativeBudget >= 1;
}
```

**问题本质**：预算系统只控制"数量"，不控制"质量"。连续两张优先级50的道侣弧线卡（感情戏）和连续两张优先级40的势力事件卡（政治戏），预算消耗一样，但情绪体验完全不同。

**关卡设计视角**：节奏控制不只是"每轮最多几件事"，而是"情绪曲线的波峰波谷"。一个道侣告白（高情绪）后面接一个势力暗流（低情绪），比接一个师尊传承（高情绪）要好得多。

#### 问题B：_narrativeQueue 优先级排序导致"重叙事优先"

```javascript
// game.js 第316行
this._narrativeQueue.sort((a, b) => 
  (b.priority || 0) - (a.priority || 0)
);
```

**问题本质**：队列按优先级降序排列，意味着高优先级叙事卡会"插队"到前面。这导致：
- 如果同时有一个道侣高潮卡（53）和一个NPC遭遇卡（30），玩家永远先看到道侣卡
- NPC遭遇卡可能被连续推迟，积压在队列里，最终在道侣线结束后一次性涌出

#### 问题C：普通卡池缺乏"情绪锚点"

```javascript
// CardSystem.js _drawNormal() 第591-662行
// 普通卡按weight随机抽取，最近8张冷却
```

**问题本质**：普通卡池是纯随机的，没有"情绪分类"。在关卡设计中，普通卡应该承担"释放区"的功能——在高紧张叙事后，给玩家一个轻松的采集/修炼卡来喘息。但当前系统完全随机，可能在道侣危机后紧接着抽到"妖兽伏击"卡。

### 3.3 优化建议

#### 建议A：引入情绪标签系统

为每张卡牌添加 `mood` 标签：`tense`（紧张）/ `neutral`（中性）/ `relax`（放松）。

在 `_drawNormal()` 中，根据最近3张卡的情绪标签，动态调整权重：
- 连续2张 `tense` → `relax` 卡权重 ×3
- 连续2张 `relax` → `tense` 卡权重 ×1.5

#### 建议B：叙事队列FIFO+优先级混合

```javascript
// 改进方案：同优先级内FIFO，跨优先级有"饥饿阈值"
// 低优先级卡等待超过5轮后，提升其优先级
const hungerBoost = Math.floor(waitTurns / 5);
effectivePriority = wrapper.priority + hungerBoost;
```

## 四、战斗遭遇设计审查

### 4.1 现状分析

**文件**：`src/systems/CombatSystem.js`

战斗系统是回合制数值对撞：
- 玩家属性：HP/ATK/DEF/CritRate/DaoResist + 灵力/架势/连击
- 敌人属性：HP/ATK/DEF/CritRate/Special
- 动作：攻击/防御/技能/终结技/架势切换/逃跑

### 4.2 发现的问题

#### 问题A：战斗遭遇无"入口可读性"

```javascript
// game.js getCurrentCard() 第450-464行
if (this.currentCard.type === 'COMBAT' || ...) {
  const entered = this._enterCombat(this.currentCard);
  // 抽到战斗卡 → 立即进入战斗，没有"预警"环节
}
```

**关卡设计原则违反**："Every combat encounter must have: entry read time"

当前设计：玩家抽到战斗卡 → 直接进入战斗界面。没有"你看到前方有妖兽"的预读阶段，玩家无法做战前准备（吃药、换装备、调整状态）。

#### 问题B：敌人配置无空间逻辑

```json
// 卡牌数据中的 enemy 字段
"enemy": {
  "name": "岩甲兽",
  "hp": 40,
  "atk": 8,
  "def": 5,
  "special": "岩甲护体",
  "specialChance": 0.2
}
```

**问题本质**：敌人是纯数值，没有"位置"概念。从关卡设计角度：
- 没有"多个敌人"的遭遇设计（全是一对一）
- 没有"敌人从哪里来"的空间叙事
- 没有"战场环境"（如秘境中战斗和宗门中战斗完全没有区别）

#### 问题C：难度缩放是纯乘数

```javascript
// CombatSystem.js _applyDifficultyScaling() 第893-909行
this.enemy.hp = Math.round(this.enemy.hp * diffMult);
this.enemy.atk = Math.round(this.enemy.atk * diffMult);
```

**问题本质**：难度只通过数值乘数调节，没有通过"机制复杂度"调节。第10次转世的敌人只是HP/ATK更高，但行为模式完全一样。好的难度曲线应该是"新机制 > 高数值"。

#### 问题D：_shouldConsumeLifespan 硬编码卡牌ID列表

```javascript
// game.js 第930-936行
_shouldConsumeLifespan(card, choice) {
  const combatIds = ['q_fellow', 'q_demon', 'q_demon2', 'q_inherit', 
    'f_mission', 'f_trial', 'cave_beast', 'cave_spirit', 'realm_guardian'];
  if (combatIds.includes(card.id)) return true;
}
```

**问题本质**：这是维护炸弹。每新增一张战斗卡，都必须手动更新这个列表。应该改为检查 `card.type === 'COMBAT'` 或 `card.tags.includes('combat')`。

### 4.3 优化建议

#### 建议A：战斗预警卡机制

在战斗卡前插入一张"预警卡"：
```json
{
  "id": "cave_beast_warning",
  "title": "低吼声",
  "description": "你听到前方传来低沉的咆哮声，地面微微震动。前方似乎有强大的妖兽。",
  "type": "COMBAT_WARNING",
  "choices": {
    "left": { "text": "正面迎战", "effects": {}, "nextCard": "cave_beast" },
    "right": { "text": "绕路而行", "effects": { "cultivation": -5 }, "nextCard": "cave_alt_path" },
    "up": { "text": "服用丹药准备", "effects": {}, "nextCard": "cave_beast_buffed" }
  }
}
```

#### 建议B：战场环境标签

为每个战斗卡添加 `battlefield` 标签，影响战斗机制：
- `cave`：洞穴战场，闪避-10%（空间狭小）
- `sect`：宗门内战斗，有道侣助战概率
- `wilderness`：野外战斗，逃跑成功率-20%
- `void`：虚空战场，灵力消耗×1.5

## 五、场景/位置叙事审查

### 5.1 现状分析

**文件**：`src/systems/SceneLayerSystem.js` + `data/locations/locations.json`

三层位置体系：
- T1：宗门/坊市/秘境/洞府/魔域/天道虚空
- T2：宗门大殿/藏经阁/炼丹房/剑崖...
- T3：隐藏位置（白落霜的狐丘/血煞地宫...）

位置卡注入优先级：28

### 5.2 发现的问题

#### 问题A：位置系统几乎完全断线

```javascript
// game.js 中搜索 sceneLayerSystem.transition 的调用点
// 只有 _advanceRealm() 中有一处：
sceneLayerSystem.transition('宗门', 'realm_breakthrough');
// 除此之外，正常游戏流程中几乎不切换位置
```

**问题本质**：整个位置系统建好了但几乎没接通。玩家从头到尾都待在"宗门"位置，位置切换只在境界突破时触发一次。这意味着：
- 位置氛围色永远不会变化
- 位置卡（优先级28）几乎不会触发
- 三层位置体系形同虚设

#### 问题B：位置与卡牌内容无关联

当前卡牌不携带位置信息。一张"采集灵草"卡和一张"宗门议事"卡，玩家所在的"位置"完全相同。

**关卡设计原则违反**："Every area tells a story through prop placement, lighting, and geometry"。在卡牌游戏中，"位置"就是叙事环境——如果玩家在"魔域"抽到"采集灵草"卡，这违和感应该被设计成叙事素材。

#### 问题C：SceneLayerSystem.loadData 从未被调用

```javascript
// SceneLayerSystem.js 第32行
loadData(data) { ... }
// 搜索全代码库，未找到调用 loadData 的地方
```

**问题本质**：locations.json 数据存在，SceneLayerSystem 的 loadData 方法存在，但从没被接上。整个系统是"建好了管道但没通水"。

### 5.3 优化建议

#### 建议A：卡牌携带位置标签

在卡牌数据中添加 `location` 字段，抽到该卡时自动切换位置：

```json
{
  "id": "q_gathering",
  "title": "采集灵草",
  "location": "宗门",  // 抽到时切换到宗门
```

## 六、流程可读性审查

### 6.1 现状分析

当前玩家可感知的进度信息：
- 顶栏：五维属性 + 修为进度条
- 章节徽章："第四章：碎丹成婴 · 3/5"
- 日志区：叙事文字流

### 6.2 发现的问题

#### 问题A：玩家无法区分卡牌来源

当一张叙事卡弹出时，玩家无法判断这是：
- 主线里程碑卡（必须看）
- 道侣弧线卡（可选关注）
- NPC遭遇卡（可选关注）
- 因果回响卡（之前选择的后果）
- 随机普通卡（可忽略）

**关卡设计原则违反**："Critical path must always be visually legible"

#### 问题B：无"下一目标"指引

玩家不知道"我现在该做什么"——是继续修炼等里程碑？还是去找支线？还是准备突破？

当前唯一的"目标"是修为条到100，但中间过程完全没有阶段性感。

#### 问题C：选择历史不可追溯

玩家做了几十个选择后，无法回看"我之前在哪些关键节点选了什么"。`gameState.choiceHistory` 存了数据但UI没有展示。

### 6.3 优化建议

#### 建议A：卡牌来源标签

在卡牌UI上添加来源标识：
- 🔴 主线（里程碑卡）
- 💜 道侣（弧线卡）
- 🟡 支线（Quest卡）
- 🔵 因果（Karma卡）
- ⚪ 普通（随机卡）

#### 建议B：阶段目标提示

在修为进度条下方添加"下一里程碑"提示：
```
修为 45/100 → 下一里程碑：师承抉择（60修为）
```

## 八、总结

一念仙途的系统架构是扎实的——20级优先级抽卡、叙事预算控制、因果种子链、四引擎弧线系统——这些是"发动机"层面的优秀工程。

但"关卡设计"层面几乎是空白的。秘境是一条管道而非一张地图，战斗是一场数值对撞而非一场战术博弈，位置系统是建好了没通水的管道，场景叙事是写了没用的剧本。

**核心建议**：不需要推翻现有系统，而是需要在现有系统上"长出"关卡设计思维。具体路径是：

1. **秘境重构**：从线性队列改为分叉地图，让玩家在秘境中有选择权
2. **位置接通**：让卡牌驱动位置切换，让玩家感受到"我在哪里"
3. **战斗预警**：在战斗前给玩家"读题时间"
4. **节奏曲线**：为普通卡池添加情绪标签，让系统自动调节紧张-释放
5. **可读性**：让玩家能看到自己在哪里、要去哪里、之前做了什么

这些改动不需要重写引擎，只需要在数据层和game.js的编排层做针对性插入。发动机已经造好了，现在需要的是好的赛道设计。
