### P0-1. 商店系统（ShopSystem）

**玩家体验目标**: 灵石有处花，花钱时有"我在修仙世界里买东西"的代入感，而不是点击一个数字。

#### Mechanic Specification

**Purpose**: 闭合经济循环（灵石来源 ✅ → 灵石消费 ❌），给玩家资源决策的战术空间

**Trigger 时机**:
- 炼气期：每 8~12 轮，10% 概率在卡牌流中插入 `shop_encounter` 卡
- 筑基期及以上：每 6~10 轮，15% 概率
- 触发卡示例：
  ```
  【坊市偶遇】
  前方出现一处修士集市，散修摆摊叫卖。
  ← 左滑：不买（继续赶路）
  → 右滑：看看（进入商店 UI）
  ```

**商店 UI 流程**:
```
触发卡右滑
  → 暂停卡牌流，弹出商店面板
  → 面板显示：当前灵石数 + 符合境界的商品列表（3~5 件）
  → 玩家选择购买 → 扣灵石 → 获得物品 → 返回卡牌流
  → 玩家选择离开 → 直接返回卡牌流
```

**商品数据结构（shop_items.json 已有，需扩展）**:
```json
{
  "id": "shop_pill_healing",
  "name": "回春丹",
  "type": "pill",
  "price": 10,
  "realm": "qi",
  "effect": { "pillId": "healing_pill" },
  "desc": "恢复气血15点。"
}
{
  "id": "shop_treasure_iron_armor",
  "name": "玄铁甲",
  "type": "treasure",
  "price": 30,
  "realm": "qi",
  "effect": { "treasureId": "玄铁甲" },
  "desc": "防御法宝。战斗时+5防御。"
}
```

**关键修复：法宝 ID 映射层**（见 P0-3）

**商品刷新规则**:
- 每个境界显示该境界及以下的商品
- 每件商品 `maxPerLifetime: 1`（法宝唯一性）
- 丹药类商品 `maxHeld: 3`（与丹药栏上限一致）

**Edge Cases**:
- 灵石不足 → 购买按钮变灰，提示"灵石不足"
- 丹药栏已满 → 提示"丹药栏已满，是否丢弃一件？"（弹出选择）
- 法宝栏已满（2 格）→ 提示"需替换一件法宝？"（显示对比）
- 转世后 → 商店商品重置（重新随机）

### P0-2. 功法被动效果接入战斗/全局

**玩家体验目标**: 选了剑修就能感受到"我很强但很脆"，选了体修就能感受到"我很难死"，而不是面板数字涨了但打架时没感觉。

#### 被动键值完整接入表

| 被动键 | 定义来源 | 应接入系统 | 接入方式 |
|---------|---------|---------|---------|
| `critRate` | 剑气纵横 / 五行精通 | CombatSystem | `_start()` 中加 `pathBonuses.critRate` |
| `daoResist` | 剑心通明 | CombatSystem / 道心伤害结算 | 暴击/特殊伤害时对 `daoHeart` 损失 × (1 - daoResist) |
| `lowHpAtkBonus` | 血剑共鸣 | CombatSystem | `_calcDamage()` 中玩家 HP < 30% 时 atk × lowHpAtkBonus |
| `maxHp` | 金刚不坏 | GameState / CombatSystem | 影响 `health * 3` 的基准值 |
| `def` | 肉身成圣 | CombatSystem | `_start()` 中加 `pathBonuses.def` |
| `SpiritStoneBonus` | 道法自然 | GameState.addResource | 灵石奖励 × (1 + spiritStoneBonus) |
| `meditationBonus` | 静心明道 | 冥想卡效果 | 修为奖励 × meditationBonus（需定义冥想卡） |
| `dungeonBonus` | 五行精通 | DungeonSystem（待建） | 秘境节点奖励加成 |
| `pillBonus` | 丹道真意 | 丹药使用效果 | 所有 `pill` 类型 effect 数值 × (1 + pillBonus) |
| `poisonResist` | 万毒不侵 | 未来中毒机制 | 毒素伤害 × (1 - poisonResist) |
| `stoneToPill` | 造化丹鼎 | 商店/丹药系统 | 灵石按汇率兑换丹药效果 |

#### 代码接入点（给工程师的指引）

**CombatSystem._start() 修改**:
```js
// 在现有功法加成之后，追加：
const pathBonuses = pathSkillSystem.getPassiveBonuses(gameState.path) || {};

// 应用被动
if (pathBonuses.critRate) critRate += pathBonuses.critRate;
if (pathBonuses.def) def += pathBonuses.def;
if (pathBonuses.maxHp) {
  // maxHp 影响气血基准：每点 maxHp = 气血上限 +1
  hp += pathBonuses.maxHp;
  maxHp += pathBonuses.maxHp;
}
// daoResist 在伤害结算和道心结算时读取
```

**daoResist 接入点**:
- `CombatSystem` 中特殊技能可能造成 `daoHeart` 损失 → 读取 `pathBonuses.daoResist`
- 卡牌效果中的 `daoHeart` 损失 → 需要在 `game.js` 的卡牌效果应用层统一读取

**pillBonus 接入点**:
- `game.js` 或 `CardSystem` 中应用 `pill` 效果时，读取 `pathSkillSystem.getPassiveBonuses().pillBonus`

**SpiritStoneBonus 接入点**:
- `gameState.addResource('spiritStone', ...)` 内部，或所有灵石奖励来源处

#### Tuning Levers [PLACEHOLDER]
- `daoResist` 效果系数：目前配置 `0.5`（减半），需测试是否太强
- `lowHpAtkBonus` 触发阈值：目前设定 30% HP，[PLACEHOLDER]
- `pillBonus` 目前配置 `0.5`（+50%），丹修过强风险

### P0-3. 法宝 ID 映射层

**问题**: `shop_items.json` 的商品 ID（`shop_treasure_iron_armor`）与 `treasures.json` 的法宝 ID（`玄铁甲`）不一致。`treasureSystem.acquire(id)` 接受的是 `treasures.json` 的 ID。

**修复方案**: 在 `TreasureSystem` 中增加映射表，或在 `shop_items.json` 的 `effect.treasureId` 中直接写 `treasures.json` 的 ID。

**推荐做法**（最小改动）:

修改 `shop_items.json`，将 `effect` 字段直接指向 `treasures.json` 的内部 ID：
```json
// 修改前
"effect": { "treasure": "shop_treasure_iron_armor" }

// 修改后
"effect": { "treasureId": "玄铁甲" }
```

同时，在 `CombatSystem._victory()` 中，奖励法宝的 `treasure` 字段也要对应修改：
```js
// 修改前（treasureSystem.acquire 接受 treasures.json 的 ID）
if (this.rewards.treasure) {
  treasureSystem.acquire(this.rewards.treasure);
  // this.rewards.treasure 现在是 "玄铁甲" 而非 "shop_treasure_iron_armor"
}
```

**映射验证脚本**（实现时顺便写）:
- 遍历 `shop_items.json` 中所有 `type: "treasure"` 的商品
- 检查 `effect.treasureId` 是否存在于 `treasures.json` 的 ID 列表中
- 启动时 `console.warn` 所有不匹配的项

### P0-4. 孤立因果卡 seed 来源（16 个）

**现状修正**: `karma.json` 中所有 16 张因果卡模板**已定义**，问题不是"卡不存在"，而是**没有任何系统在任何时机种下对应的 `karmaSeed`**。

**设计原则**: 每个 seed 来源必须符合 GDD 的因果设计哲学——"玩家能回忆起导致后果的那次决策"。

#### Seed 来源分配表

| Seed ID | 对应因果卡 | 种下时机 | 设计理由 |
|---------|-----------|---------|---------|
| `combatScar` | `k_combat_scar` | 战斗卡胜利后，若玩家 HP < 30% | 重伤留下病根，合理 |
| `combatGlory` | `k_combat_glory` | 战斗卡胜利后，若敌人是 `factionId` 关联的重要敌人 | 战名远扬 |
| `companionSacrifice` | `k_comp_sacrifice` | 道侣事件中，选项导致道侣受伤时由事件代码种下 | 道侣为你牺牲→后续回报或创伤 |
| `companionTrust` | `k_comp_trust` | 道侣信任度变化事件，若 `trust < 20` 时选择信任选项 | 信任来之不易 |
| `factionUprising` | `k_faction_uprising` | `FactionSystem` 中 `undercurrentStage` 推进到 `>= 2` 时 | 势力矛盾爆发 |
| `factionPeace` | `k_faction_peace` | 玩家成功调停势力事件时（如果有） | 和平结局的善因 |
| `lifespanWaste` | `k_lifespan_waste` | `gameState.resources.lifespan < 20` 时，由 `game.js` 每轮检测 | 寿元告急的危机感 |
| `fortuneWheel` | `k_fortune_wheel` | 玩家使用"拨动天机盘"功能时（未来功能）或获得稀有法宝时 | 天机不可泄露 |
| `betrayedNpc` | `k_betrayed_npc` | NPC 好感度事件中选择"信任后被背叛"的选项 | 具体 NPC 事件 |
| `spellHidden` | `k_spell_hidden` | 法修玩家在"天枢道院"相关事件中触及禁术时 | 已部分存在（skill_2 事件） |
| `spellRevealed` | `k_spell_revealed` | `spellHidden` 发芽后的后续 | 连锁因果 |
| `pillPoison` | `k_pill_poison` | 丹修玩家使用"失传丹方"或"禁药"时 | 丹道风险 |
| `pillCure` | `k_pill_cure` | `pillPoison` 发芽后的后续 | 连锁因果 |
| `whiteFox` | `k_fox_returns` | **已有**：白狐支线卡牌中种下 ✅ | 无需处理 |
| `swordBetrayed` | `k_sword_betrayal` | 剑修传承 Step4 的选项（"同门背叛"分支） | 需补充进剑修传承事件 |
| `swordHonor` | `k_sword_honor` | 剑心通明事件中获得剑佩后的后续 | 需补充进剑修传承事件 |

#### 实现优先级（先打通最有影响力的）

**第一批（直接接入现有系统）**:
1. `combatScar` — 在 `CombatSystem._victory()` 中，若 `player.hp < maxHp * 0.3`，调用 `karmaSystem.addSeed({ id: 'combatScar', ... })`
2. `lifespanWaste` — 在 `game.js` 的主循环 `advanceTurn()` 中，若 `lifespan < 20`，种下 seed
3. `factionUprising` — 在 `FactionSystem.advanceUndercurrent()` 中，当 stage 推进到触发点时种下 seed
4. `companionSacrifice` — 在 `CompanionSystem.applyChoice()` 中，若选项导致道侣受伤，种下 seed

**第二批（需要补充卡牌内容）**:
5. `swordBetrayed` / `swordHonor` — 需在剑修传承事件中补充 karmaSeed 字段
6. `spellHidden` / `spellRevealed` — 需确保天枢道院事件链完整触发
7. `pillPoison` / `pillCure` — 需确保丹修失传丹方事件链完整触发

**Edge Cases**:
- 同一 seed 已存在 → `karmaSystem.addSeed()` 应该去重（根据 seedId）
- seed 对应的因果卡已被玩家看过（`once: true` 且已触发）→ 不重复发芽
- 转世后 → seed 以"宿命卡"形式保留（已有机制）

### P1-3. 道侣 bondDelta 核实与补全

**现状修正**: 经核查 `data/companions/events.json`，**bondDelta 字段实际已存在于关键事件中**：
- 白落霜：`blx_6`（人妖殊途）左滑 `bondDelta: 1` ✅
- 白落霜：`blx_7`（狐牙）左滑 `bondDelta: 1` ✅
- 白落霜：`blx_9`（生死相依）左滑 `bondDelta: 1` ✅
- 白落霜：`blx_10`（天命道侣）左滑 `bondDelta: 1` ✅
- 剑灵儿：`jle_7`（冰心化暖）左滑 `bondDelta: 1` ✅

**剩余问题**: 部分道侣的事件中 bondDelta 还不够密集，导致情劫触发太慢。

**修复**: 为每个道侣的每个 `type: "emotional"` 事件的正面选项加上 `bondDelta: 1`（目前只有 `crisis` 和少数 `emotional` 有）。

**情劫触发条件复核**:
- `checkTribulation()` 要求 `bond >= 3` 且 `realm === 'golden'`
- 按目前数据，玩家需要与道侣经历至少 3 个有 `bondDelta` 的事件才能达到 `bond: 3`
- 这在金丹期是合理的——情劫应该是"经过一段感情发展后"才触发

**结论**: P1-3 的优先级下调。实际问题是"部分道侣事件不够多，导致 bond 增长慢"，解法是为每个道侣补充 2~3 个 `daily` 或 `emotional` 事件。

### P1-4. 转世记忆卡触发条件

**现状**: `karma.json` 中已有 3 张转世记忆卡：
- `k_echo_past_life`（前世回响）— `requirements.minLifeCount: 1`
- `k_echo_path_mastery`（功法记忆）— `requirements.minLifeCount: 2, differentPaths: true`
- `k_echo_karma_chain`（三世因果）— `requirements.minLifeCount: 3`

**问题**: `CardSystem` 中没有代码检查 `requirements.minLifeCount` 并把这些卡加入卡池。

**修复方案**: 在 `CardSystem._buildCardPool()` 或卡牌权重计算中，加入：
```js
// 检查转世记忆卡的解锁条件
if (card.requirements && card.requirements.minLifeCount) {
  if (gameState.lifeCount < card.requirements.minLifeCount) {
    return 0; // 权重为 0，不出现
  }
}
```

**Players experience**: 转世一次后，在炼气/筑基期有概率抽到"前世回响"卡，让玩家感受到"这一世和上一世是连着的"。

### P2-2. 多结局系统

**GDD 设计**（第十八节）: 8 个结局（3 主 + 3 分支 + 2 隐藏）

**现状**: 只有飞升一个结局在 `game.js` 中引用了 `ending_ascension` 卡。

**实现指引**:

在 `game.js` 的飞升/渡劫结算处，计算结局分数：
```js
function calculateEnding() {
  const netKarma = gameState.attributes.karmaGood - gameState.attributes.karmaBad;
  const daoHeart = gameState.attributes.daoHeart;
  const hasCompanion = gameState.resources.companions.length > 0;
  const companionAff = hasCompanion ? companionSystem.getState(gameState.resources.companions[0]).affection : 0;
  
  // 优先级判断（见 GDD 第十八节）

  if (hasCompanion && companionAff >= 80) return 'ending_reunion';

}
```
